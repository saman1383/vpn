# نصب نسخه متصل ویرا روی cPanel

این بسته با نسخه نمایشی قدیمی `downloads/vira-cpanel.zip` متفاوت است. React در مرورگر، PHP روی هاست و MySQL محل نگهداری کاربران، سفارش و سرویس‌ها است. برای انتشار نیاز به Node روی هاست نیست.

## پیش‌نیاز و وضعیت تست

- PHP 8.2 یا جدیدتر، ۶۴ بیتی، افزونه‌های PDO MySQL، cURL، mbstring، session و JSON؛ MySQL 8 یا MariaDB سازگار با InnoDB و GET_LOCK.
- دامنه با HTTPS فعال (AutoSSL)، دسترسی خروجی HTTPS هاست به زرین‌پال و پنل، و امکان اجرای PHP CLI یا Terminal در cPanel.
- قرارداد API این پیاده‌سازی: **MHSanaei/3x-ui v3.11.0** و مسیرهای `/panel/api/clients/add`، `/clients/get/{email}`، `/clients/update/{email}` و `/clients/traffic/{email}`. برای نسخه 2.x مناسب نیست. قبل از استفاده نسخه پنل و سازگاری API را بررسی کنید.
- مبنای قرارداد: https://github.com/MHSanaei/3x-ui/blob/v3.11.0/docs/public/openapi.json
- اتصال با Bearer API token است، نه نام کاربری و رمز پنل. توکن با امکان خواندن و ایجاد/ویرایش client در بخش API پنل ساخته شود؛ توکن monitor کافی نیست.
- فعلاً یک پنل با چند inbound پشتیبانی می‌شود. ابتدا یک inbound **VLESS یا VMess با quota و expiry مثبت، بدون reset خودکار ترافیک** برای فروش اختصاص دهید. مدیریت همزمان همان client در ابزار دیگر توصیه نمی‌شود؛ می‌تواند با بازیابی سفارش تداخل کند. محدودیت دستگاه در این نسخه `limitIp` است، نه شمارش قطعی دستگاه یا HWID.
- تست واقعی زرین‌پال، MySQL روی هاست و اتصال زنده 3x-ui بدون دسترسی به سرویس‌های شما انجام نشده است. قبل از عرضه عمومی، سناریوهای انتهای راهنما را اجرا کنید. این بسته را صرفاً به دلیل موفق بودن build آماده فروش فرض نکنید.

## ساخت بسته

روی رایانه/محیط توسعه:

```sh
npm ci
npm run package:cpanel
```

فایل `vira-cpanel-connected.zip` دو پوشه دارد:

```
public_html/       فایل‌های سایت و api/index.php
vira-private/      PHP، schema و نمونه تنظیمات؛ نباید عمومی باشد
```

## نصب

1. در File Manager وارد **پوشه خانه اکانت** مثل `/home/USERNAME` شوید، نه داخل public_html. بسته را آنجا Extract کنید. ابتدا از سایت و دیتابیس موجود بکاپ بگیرید. برای addon domain فایل‌های public_html بسته را به Document Root همان دامنه منتقل کنید و مسیر خصوصی را طبق مرحله ۴ مشخص کنید.
2. در MySQL Database Wizard دیتابیس و کاربر بسازید و تمام مجوزهای دیتابیس اختصاصی را به همان کاربر بدهید.
3. فایل `vira-private/config.example.php` را به `config.php` کپی کنید. اطلاعات دیتابیس، `site_url` (بدون / انتهایی)، merchant_id، panel_url (همراه مسیر مخفی، بدون `/panel/api`)، panel_token و subscription_url را **فقط روی هاست** وارد کنید. مجوز پوشه خصوصی 700 و config.php برابر 600 باشد. اطلاعات محرمانه را در چت، React، Git یا public_html نگذارید.
4. مسیر پیش‌فرض API: پوشه `vira-private` کنار public_html. اگر Document Root متفاوت است، در `api/index.php` مقدار `$private` را به مسیر مطلق همین پوشه خصوصی تغییر دهید یا متغیر محیطی `VIRA_PRIVATE_DIR` را روی هاست تنظیم کنید. `.htaccess` خصوصی دفاع دوم است؛ فایل خصوصی هرگز داخل document root نباشد. open_basedir هاست باید خواندن این مسیر را مجاز بداند.
5. در Terminal اجرا کنید (ممکن است مسیر PHP هاست مثل `/opt/cpanel/ea-php82/root/usr/bin/php` باشد):

```sh
cd /home/USERNAME/vira-private
php console.php install
```

اگر Terminal ندارید schema.sql را با phpMyAdmin Import کنید. فایل نصب عمومی روی وب ایجاد نکنید.
6. وارد سایت شوید و حساب اصلی را ثبت کنید. سپس فقط از Terminal آن را مدیر کنید:

```sh
php console.php admin owner@example.com
```

بدون Terminal، پس از ثبت‌نام در phpMyAdmin فقط ردیف ایمیل صاحب سایت را در جدول users پیدا کنید و role را admin کنید. نقش از فرم ثبت‌نام یا مرورگر پذیرفته نمی‌شود.
7. از بخش مدیریت، پلن بسازید؛ قیمت **تومان**، حجم **GiB**، روز، محدودیت IP و inbound_id واقعی را وارد کنید. مبلغ ارسال‌شده به زرین‌پال **ریال** و از قیمت سمت سرور محاسبه می‌شود. هر پلن باید inbound معتبر داشته باشد. قیمت‌های دمو مبنای فروش نیستند.
8. در Cron Jobs هر پنج دقیقه اجرا کنید (مسیرها را اصلاح کنید):

```sh
/opt/cpanel/ea-php82/root/usr/bin/php /home/USERNAME/vira-private/console.php retry
```

Cron فقط سفارش‌های پرداخت‌تأییدشده را تحویل/بازیابی می‌کند؛ پرداخت تأییدنشده با دکمه بررسی توسط مالک/مدیر مجدداً از درگاه استعلام می‌شود.
9. در صورت عدم نیاز به ثبت‌نام جدید، registration را false کنید. HTTPS باید اجباری باشد؛ session cookie امن است و روی HTTP کار نمی‌کند. به صورت روزانه از دیتابیس و تنظیمات خصوصی پشتیبان امن بگیرید.

برای نصب زیرپوشه قبل از ساخت، `npm run build -- --base=/vira/` با `VITE_APP_MODE=connected` را اجرا و بسته را با همان dist جایگزین کنید؛ site_url نیز باید پسوند /vira داشته باشد. بسته پیش‌فرض برای ریشه دامنه است.

## جریان پرداخت و بازیابی

- callback صرفاً از Authority برای پیدا کردن سفارش استفاده می‌کند؛ Status=OK به تنهایی اعتبار ندارد. amount از دیتابیس خوانده شده و verify سمت سرور انجام می‌شود. کدهای 100 و 101 همراه ref_id پذیرفته می‌شوند؛ ref_id یکتا است.
- وضعیت‌ها: requesting → pending → paid → fulfilled. تا پیش از paid ایجاد/تمدید انجام نمی‌شود. سفارش paid که ساخت آن شکست خورده از بین نمی‌رود و دوباره قابل پردازش است. ابتدا سفارش paid قدیمی همان کاربر تحویل داده می‌شود.
- برای هر درخواست checkout شناسه یکتا وجود دارد؛ قفل دیتابیس مانع اجرای موازی همان سفارش/کاربر می‌شود. هدف حجم/تاریخ و هویت client قبل از تماس با پنل ذخیره می‌شود. retry مقدار مطلق قبلی را اعمال می‌کند، نه تمدید مجدد. در create، email و subId ثابت با رفتار dedup نسخه مشخص پنل استفاده می‌شوند.
- تمدید حجم را به سهمیه قبلی اضافه می‌کند و تاریخ را از بزرگ‌ترِ اکنون/انقضای قبلی افزایش می‌دهد؛ مصرف صفر نمی‌شود. سرویس نامحدود و تغییر inbound در تمدید پذیرفته نمی‌شود.
- اگر درخواست اولیه درگاه قطع شود، سفارش requesting ممکن است نیازمند تطبیق دستی در داشبورد زرین‌پال باشد. خودکار درخواست جدید صادر نمی‌شود. مدیر باید ابتدا قطعیت عدم پرداخت/مرجع پرداخت را در درگاه روشن کند؛ رکورد پرداخت را دستی paid نکند. صفحه مدیریت فعلاً ابزار refund، لغو یا reconcile خودکار ندارد.
- فراموشی رمز/تأیید ایمیل، کیف پول، چند پنل، تخفیف دلخواه، گزارش‌های پیشرفته و ویرایش کامل کاربر هنوز در حالت واقعی پیاده نشده‌اند. امکانات مشابه در حالت دمو به سرویس واقعی متصل نیستند. لینک اشتراک محرمانه است و نباید منتشر شود.

## چک‌لیست اجباری پیش از فروش

1. ثبت‌نام/ورود/خروج و عدم دسترسی کاربر عادی به API مدیر، تیکت و سفارش دیگران.
2. خرید کم‌مبلغ واقعی، تطبیق مبلغ ریالی/شناسه پیگیری و دریافت config قابل اتصال از subscription URL.
3. callback تکراری، Refresh، دکمه retry و قطع ارتباط بلافاصله پس از add/update: فقط یک سرویس و یک افزایش حجم/مدت.
4. پرداخت لغوشده یا Authority جعلی: هیچ سرویس جدیدی ایجاد نشود. مبلغ دست‌کاری‌شده مرورگر اثری نداشته باشد.
5. خاموش بودن پنل پس از پرداخت: سفارش paid باقی بماند و با Cron یا retry بدون پرداخت دوباره تحویل شود.
6. تمدید سرویس منقضی/فعال، تطبیق حجم باقیمانده و نمایش ترافیک واقعی، اعتبار TLS و permission مسیر خصوصی.
7. بررسی لاگ خطاهای PHP هاست؛ پاسخ عمومی عمداً جزئیات حساس دیتابیس/پنل را نشان نمی‌دهد. تغییر API نسخه پنل نیازمند آزمون مجدد است.

حالت پیش‌فرض `npm run dev` و `npm run build` هنوز دمو است؛ فقط `npm run package:cpanel` یا build با `VITE_APP_MODE=connected` حالت واقعی را فعال می‌کند. در حالت واقعی، خرابی API هرگز باعث ورود خودکار به دمو یا دسترسی آزاد به مدیریت نمی‌شود. نصب Docker قدیمی فقط برای دمو است.
